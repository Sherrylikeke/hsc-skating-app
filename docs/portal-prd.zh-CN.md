# HSC 官网迁移产品需求文档

版本 0.9　日期 2026年11月19日　状态 已确认 Stripe Payments 分期实现待定

本项目在现有 HSC 应用上扩展俱乐部门户，将 HSC 自有官网、会员报名及收费业务迁出 Uplifter。原网站的信息结构、功能和主要操作习惯作为产品基线，视觉设计为主要改进范围。现有赛程、账号和私人权限继续保留；沿用当前前后端及数据库，增加应用内轻量内容后台，采用 Stripe Payments；其余组件、分期方式和部署调整逐项确认。

## 1 产品目标与已确认决策

成功后的家长仍能按原有栏目找到课程、教练、政策和报名入口，沿熟悉的流程注册、选课和付款。Board 能维护内容、管理报名与收费，俱乐部掌握相关数据及运营权限。

| 决策编号 | 事项 | 当前决定 |
| --- | --- | --- |
| D01 | 产品结构 | 保留原站栏目、层级、主要入口和信息归属 |
| D02 | 功能与体验 | 功能保持等价，主要操作顺序和使用习惯保持熟悉 |
| D03 | 视觉范围 | 重点更新外观，包括字体、颜色、间距、图片及控件表现 |
| D04 | 迁移终态 | HSC 自有门户、报名和收费脱离 Uplifter 日常依赖 |
| D05 | 与现有应用的关系 | 用户已选择在现有 HSC 应用上扩展 |
| D06 | 技术选型 | 前后端及数据库已确认沿用现有技术；其余组件、服务商及托管方式逐项确认 |
| D07 | 内容管理 | 已确认应用内轻量后台；Board 使用现有账号，按批准的内容权限操作 |
| D08 | 文件存储 | 已确认 R2 存图片和 PDF；Worker 控制上传与访问，D1 保存文件记录 |

| D10 | 支付服务商 | 已确认采用 Stripe Payments；Stripe Billing 及分期实现另定 |

首次上线范围是现有业务的完整替代，不加入新 CRM、在线投票、捐款平台、营销自动化或新的原生手机功能。现有赛程应用的既有功能继续保留。后台产品是否需要额外功能，以实际旧后台核验为准。

价格、退款、报名门槛、政策条款和授权语义不属于视觉调整。发现错误时建立差异记录，确认后修复；未确认项不得成为收费配置。原站英文栏目和业务名称默认保留，门户新增语言另行讨论。

## 3 视觉更新与交互等价要求

| 编号 | 可以调整的表现 | 必须保留的行为或含义 |
| --- | --- | --- |
| UX01 | 品牌颜色、字体、字号、间距、背景和边框 | 栏目命名、层级、阅读内容及操作目的 |
| UX02 | 通用横幅尺寸、照片裁切和页面留白 | Logo、俱乐部身份、图片用途和信息归属 |
| UX03 | 卡片、按钮、表格、输入框和状态提示样式 | 主要操作标签及用户辨认方式，例如 Register 与 Add to Cart |
| UX04 | 桌面和手机自适应布局 | 同一任务的字段、业务步骤、返回关系及结果 |
| UX05 | 键盘焦点、表单标签、对比度、错误提示可读性 | 验证规则与业务处理结果，不暗中提高或放宽门槛 |
| UX06 | 课表和附件的可读性 | Schedule 仍是课表入口，原 PDF 下载能力保留 |

默认保留列表与日历切换、课程详情展开、未登录报名时的登录提示和返回报名上下文。支付服务商所需验证可能增加步骤，应明确列为技术约束与体验差异，不能宣称完全复制原结账。

对每条核心任务建立旧流程与新流程对照，记录入口、页面顺序、字段、按钮、错误和完成状态。已经观察到的部分按原流程验收；登录后未核验部分先补证据，再冻结设计。关键步骤增减、栏目搬迁或默认值变化需作为产品变更单独确认。

视觉方案先展示首页、课程报名、登录及商品页四个代表页面，再展开全站。用户尚未选定具体配色、字体或视觉风格，本 PRD 不锁定设计稿。

## 4 功能需求与主要流程

下列“公开已见”表示有页面证据；“规则已见”表示公开文字提及但后台计算未核验；“待后台”表示需要后台或会员流程补证据。必要的新系统内部实现不得伪称为原站已验证功能。

| 编号 | 功能要求 | 证据与验收依据 |
| --- | --- | --- |
| FR01 | 保留首页、介绍、课程、教练、资源、课表、新闻及联系页面 | 公开已见；逐页内容和链接映射齐全 |
| FR02 | 保留家庭账户、选手关联、登录、注册、找回密码和邮件偏好能力 | 公开表单已见；登录后家庭管理待后台 |
| FR03 | 保留课程搜索、筛选、排序、详情、列表和日历视图 | 公开已见；同条件返回同等业务结果 |
| FR04 | 选手报名、容量、候补、资格和报名开放限制按原业务规则承接 | 部分公开已见；实际判断与候补处理待后台 |
| FR05 | 购物车、费用明细、政策确认、结账、结果及收据功能等价 | 登录门槛已见；完整流程待后台 |
| FR06 | 保留家庭折扣、多课折扣、条件价、会员年费和定金处理 | 规则已见；优先级、叠加及取整待核对 |
| FR07 | 保留一次性付款、分期、线下收款确认、退款和信用余额等实际在用能力 | 规则已见；当前启用方式、状态和权限待后台 |
| FR08 | 保留商品数量、售罄和购买；按实际配置承接尺码与刺绣字段 | 公开目录已见；购买后配置及履约待后台 |
| FR09 | 保留志愿者入口及实际岗位业务 | 登录门槛已见；岗位、申请、审核待后台 |
| FR10 | 保留联系表单的姓名、邮箱、部门、留言及防滥用能力 | 公开已见；收件人和投递验证待补 |
| FR11 | Board 可维护现有内容并执行报名、会员和财务运营 | 业务替代要求；旧后台流程与角色范围待补 |
| FR12 | 现有赛程、主页选手、教练和私人资料权限不退化 | 现有应用约束；相关服务端回归必须通过 |

家长选课流程基线：原栏目入口 → 找到课程 → 看详情 → 登录或创建账号 → 回到报名上下文。之后的选手选择、政策确认、购物车和付款步骤，按实际旧流程补齐，不凭经验确定顺序。

商品与年费流程基线：目录 → 数量或购买入口 → 未登录时提示登录。后续选手归属、商品选项、已购买判断、结账和收据同样待核验。

旧后台界面无法从公开页重建。管理员的任务、字段、结果和权限等价属于本项目范围；后台外观及操作方式在获得演示或导出后确认。

## 5 收款与数据迁移要求

| 编号 | 要求 | 完成条件 |
| --- | --- | --- |
| PAY01 | 采用 Stripe Payments，收款账户归 HSC；新订单不依赖 Uplifter 创建或结算 | 明确账户归属、结算银行及操作权限 |
| PAY02 | 服务端按可信支付结果更新订单与报名 | 成功、失败、取消、延迟及重复通知均有确定结果 |
| PAY03 | 名额占用与付款状态一致 | 同时争抢最后名额不超卖；超时与失败按确认规则释放 |
| PAY04 | 金额、币种、折扣、税费和取整来自服务端确认规则 | 用户端改参数不能改变应收；样本账单逐项一致 |
| PAY05 | 有限期分期、定金、欠款、信用余额和退款分别记录 | 未到期分期总额与旧账一致；不重复收取定金或年费 |
| PAY06 | 卡号和银行资料交支付商处理 | 应用仅保存必要引用及结果；迁卡由支付商安全转移或重新绑定 |
| DAT01 | 保留旧会员、选手、班次、订单等 ID 映射 | 历史记录可追溯，同名不自动合并 |
| DAT02 | 迁移同意记录、版本、接受时间和邮件偏好 | 缺失记录标为未知，不伪造已同意或已验证 |
| DAT03 | 与现有 HSC 账号建立经过验证的关联 | 姓名、邮件字符串或主页偏好不自动授予私人关系 |
| DAT04 | 历史交易及开账余额可复核和导出 | 总额与逐户样本都通过财务核对，差异可解释 |

现有应用的登录和账户恢复路径保留。Uplifter 密码能否导出及适配尚未知；默认准备安全激活或设置密码的迁移方式。不得为了兼容旧站注册表单而削弱现有服务端权限、邮箱状态或邀请范围。

协会会员号、年度已收费和协会已登记状态应分别保留。外部协会平台、私教和其他独立服务的支付入口按原职责保留，不在未确认商户关系时纳入 HSC 结算。

切换前导出并演练；切换时核对增量资料、正在处理的支付与未到期分期，确保同一笔未来款项只有一处执行。旧渠道的退款、争议和档案保留期限按实际合同确认，再完成退出。

## 6 权限与质量要求

角色表是新业务所需的职责划分，尚不是对 Uplifter 现有角色名称的断言。具体授权边界需与实际管理方式核对。

| 角色 | 应有能力 | 权限边界 |
| --- | --- | --- |
| 访客 | 浏览公开页面、课程和商品 | 不读取会员私人资料 |
| 家长或会员 | 操作本人账户及获准关联选手的报名和账单 | 不凭姓名认领他人或看到他人财务 |
| 内容编辑 | 维护公开页面、公告、教练与文件 | 不默认获得退款或私人关系管理权 |
| 报名管理 | 处理班次、名单、候补和经授权调整 | 财务写入范围另行明确 |
| 财务 | 核对收款、余额、分期、退款和报表 | 关键操作留痕；不默认管理全部私人内容 |
| 管理员 | 管理账户角色及批准关系 | 服务端校验；Board 头衔不自动授予全部权限 |

NFR01 所有私人读取和写入由服务端检查；保留现有 Origin、会话撤销、角色及关系控制。新增报名资格和缴费状态不能自动扩大赛程应用的私人授权。

NFR02 手机和桌面完成相同任务，正常缩放与键盘操作可用；表单错误应指出问题并保留可保留的输入。页面不得出现阻挡主要操作的溢出或遮挡。

NFR03 重要内容、价格、订单、角色和退款修改记录操作人、时间和前后状态。备份可恢复、导出可读取，董事交接和离任撤权有明确操作路径。

NFR04 负载目标、可用性目标、备份恢复时间、邮件时效和数据保留期限均待结合实际规模确认。本版本不承诺未测量的性能数字。

## 7 验收与发布条件

| 编号 | 验收内容 | 通过标准 |
| --- | --- | --- |
| AC01 | 结构与链接 | 31 个已知入口都有保留或说明明确的对应；导航层级与信息归属一致 |
| AC02 | 内容与素材 | 页面、6 份 PDF、视频及图片逐项清点；失效或受限外链单独处理 |

| AC04 | 规则等价 | 确认后的价格、资格、折扣、分期、年费和退款样本计算正确 |
| AC05 | 支付异常 | 成功、失败、取消、超时、延迟、重复回调及名额竞争不产生错单或重复入班 |
| AC06 | 财务迁移 | 订单、已付、欠款、余额和剩余分期总额及逐户样本对齐 |
| AC07 | 权限与现有功能 | 账号隔离及越权测试通过；现有 HSC 相关回归通过 |
| AC08 | Board 运营 | 内容、报名和财务负责人完成各自实际任务；操作记录可查 |
| AC09 | 设备与邮件 | 手机和桌面主要流程验收；真实邮件送达在单独授权后验证 |
| AC10 | 切换与退出 | 演练、备份恢复、旧分期停扣、新分期启用和旧退款渠道均有执行记录 |

公开页面的展示验收不能代替登录后及财务验收。没有后台资料时，可完成公开站点设计和隔离原型，但不能宣称整个 Uplifter 功能已等价替代。真实付款、邮件、域名与生产切换按后续明确授权执行。

故障回退须先核对新系统已经产生的订单和付款，再恢复入口或支付计划，不能直接重启旧分期造成双重扣款。业务是否回退和支付如何处理需要对应负责人执行。

## 8 技术决策与下一步

2026年11月18日已确认在现有应用扩展，沿用前端、Worker、D1 和 Drizzle，采用应用内轻量后台及 R2 文件存储；其余选型逐项确认。

复用前端、构建及认证授权；Worker 扩展报名、订单和支付通知。无需升级框架依赖，新增功能须通过相关回归。

D1／Drizzle 按 SQLite 语义只追加业务表和迁移，保留会员、赛程、关系和历史；不重建库或修改旧迁移。R2 存图片和 PDF，D1 记录文件键、类型、大小、版本和可见性。Worker 校验上传与访问；草稿及受限附件不公开。实际开通、绑定、费用和备份待定。

| 顺序 | 决策项 | 当前状态与需要比较的内容 |
| --- | --- | --- |
| T01 | 应用边界 | 已确认在现有 HSC 应用扩展；不新建替代站点或数据库 |
| T02 | 前端技术 | 已确认沿用 TypeScript、React、Tailwind、当前 Next 路由体系和 Vinext与Vite 构建方式 |
| T03 | 后端及部署 | 后端已确认沿用 Cloudflare Worker；托管账户及部署方式待定，不默认迁入个人账户 |
| T04 | 数据库和文件存储 | 已确认 D1、Drizzle 及 R2；在原库追加业务表，R2 实际绑定、费用及备份待定 |
| T05 | 内容管理 | 已确认应用内轻量后台，复用账号与授权；独立 CMS 比较留档，不接入候选平台 |
| T06 | 账号与数据关联 | 保留既有认证安全基线；确认旧会员激活、家庭关系及去重流程 |
| T07 | 支付与分期 | 已确认线上报名为主，采用 Stripe Payments；Billing、分期方式及旧卡迁移待定 |
| T08 | 邮件与通知 | 待确认服务、发件域名、模板和投递；现有功能与注册限制保留 |
| T09 | 域名及路由安排 | 待确认公众首页、原赛程入口、登录和旧链接映射；不默认改 DNS |
